---
hoglake: minor (Server)
---

A Hoglite catalog's S3 prefix is now trusted from the hoglite tenant manifest, not from the tenant's own `meta.data_path` row (#668). The catalog create sends the `data_path` to hoglite, which stores it in the manifest and repeats it in the `X-Hoglite-Data-Path` header of every tenant answer; cleanup, compaction, upload claims and the catalog drop act on that value. A row that differs is audited and counted (`hoglake_hoglite_data_path_mismatch_total`), a create naming a different path for an existing tenant is a 409, and a scan, file listing or changefeed drops a file whose path lies outside the prefix (`hoglake_path_outside_data_path_total`). On both backends every object-store view a job takes is bounded to the catalog's prefix: a path outside it fails per key before any S3 call, so a removal row naming another catalog's object stays queued. Compaction's planning skips such a file as an input instead of failing the group every run. A Hoglite catalog created before hoglite held the field answers 409 `data_path_unverified` to cleanup, compaction and upload claims until it is dropped and created again; reads, commits, expiry, retirement and the expired-upload sweep (which only queue removal rows) are unaffected, so it can still be emptied, though not dropped through the API once a removal is queued (see Operators). That reading is per tenant: once a hoglake process has seen a tenant's data_path, an answer without the header is refused (503 on a read, `commit_outcome_unknown` on an applied write) rather than read as legacy. A `data_path` must be printable ASCII on both backends (it travels in that header). A create that fails after the tenant PUT never deletes the tenant, and a retry with the same `data_path` completes it ("already exists" is decided from the tenant's schema, never from hoglite's create answer); a drop removes a tenant whose catalog never bootstrapped (a `meta` table without its row is refused as damage), and hoglite's 400 `invalid_data_path` on a create is a 422. hoglite's own cross-tenant `data_path` overlap refusal surfaces as the 422 the PostgreSQL overlap check answers. Requires a hoglited that serves `X-Hoglite-Data-Path`; on an older engine a catalog create fails with 503 rather than create a catalog that could never be maintained; the tenant it made stays for an operator to remove. Operators: a legacy Hoglite catalog (dev only, none in prod) with removal rows queued can never drain them and so can never be dropped through the API; delete its objects by hand, remove its tenant with hoglite's `DELETE /v1/tenants/{tid}`, and create the catalog again.
