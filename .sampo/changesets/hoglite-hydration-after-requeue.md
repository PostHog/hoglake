hoglake: minor (Server)

Hoglite catalogs hydrate column stats (#675). Hoglite has no hydrator loop, so a file committed without `column_stats` stayed `pending` forever and scans could not prune it. `POST /v1/catalogs/{catalog}/maintenance/rehydrate` on a Hoglite catalog now requeues `failed` files as before and then runs one bounded hydration sweep over the same scope: up to 1,000 live `pending` files of live tables, started within 10 s, with the PostgreSQL hydrator's footer read, aggregate, record-count check, field-id audit, split offsets, `HOGLAKE_HYDRATOR_MIN_FILE_BYTES` floor and object-prefix quarantine. Files already pending go before the ones the requeue flipped, so files that fail on every call cannot hold back newer ones. A file whose table is altered during the sweep stays `pending` and counts only as `claimed`; a file that cannot be hydrated is marked `failed` and the sweep goes on; a file whose path is outside the catalog's `data_path` is marked `failed` without being read. A width-changing promote that races the sweep replans, so the hydrated bounds are re-encoded. The promote replans once; if the sweep moves the table's stat-less file count again it answers 409 `commit_conflict` and is safe to retry. The sweep records its own `hydrator` run in the maintenance ledger; its failure is logged and does not fail the response, whose body is unchanged. Call the route again to drain a larger backlog (`pending_files` in `GET /maintenance/status`). `GET /maintenance/status` on a Hoglite catalog now reports the hydrator with no `loop_interval_ms` and a null `loop` (manual only) instead of a configured interval for a loop that never runs. A file without field ids that is still `pending` when its column is promoted (`int` to `long`, `float` to `double`) hydrates with the promoted type's 8-byte bounds; the PostgreSQL hydrator's same fix is split out into its own PR.
