hoglake: minor (Server)
---

Hoglite catalogs hydrate column stats (#675). Hoglite has no hydrator loop, so a file committed without `column_stats` stayed `pending` forever and scans could not prune it. `POST /v1/catalogs/{catalog}/maintenance/rehydrate` on a Hoglite catalog now requeues `failed` files as before and then runs one bounded hydration sweep over the same scope: up to 1,000 live `pending` files of live tables, started within 10 s, with the PostgreSQL hydrator's footer read, aggregate, record-count check, field-id audit, split offsets, `HOGLAKE_HYDRATOR_MIN_FILE_BYTES` floor and object-prefix quarantine. The sweep starts after the highest file id of a live table the requeue found `failed` and wraps to the lowest ids, so files that fail on every call rotate through the sweep and cannot hold back newer ones. A file whose table is altered or dropped, or which ends, during the sweep stays `pending` and counts only as `claimed`, whether its footer was good or not; a file that cannot be hydrated is marked `failed` and the sweep goes on. Stats or split offsets over the scan's 64 KiB per-file limit are not stored, so a wide file is scanned without bounds instead of refused. A width-changing promote that races the sweep replans, so the hydrated bounds are re-encoded; its fence counts the catalog's live `pending` and `failed` files through `files_live_stats`, not the table's retained manifest. A fence trip from the sweep shares the promote's budget of 3 file-set replans; the 4th answers 409 `commit_conflict` and is safe to retry. The sweep records its own `hydrator` run in the maintenance ledger, including what it resolved before a failure; its failure is logged and does not fail the response, whose body is unchanged. Call the route again to drain a larger backlog (`pending_files` in `GET /maintenance/status`). `GET /maintenance/status` on a Hoglite catalog now reports the hydrator with no `loop_interval_ms` and a null `loop` (manual only) instead of a configured interval for a loop that never runs. A file without field ids that is still `pending` when its column is promoted (`int` to `long`, `float` to `double`) hydrates with the promoted type's 8-byte bounds; the PostgreSQL hydrator's same fix is split out into its own PR.

A Hoglite tenant can rewrite its own `meta.data_path` and `files.path` (#668), so the sweep reads footers only under a prefix the tenant cannot write. New `HOGLAKE_HOGLITE_DATA_PATH_TEMPLATE` (for example `s3://warehouse/{catalog}`; it must contain `{catalog}`) names it. Without it, the sweep reads through the `broker` provider's per-catalog session, asked for with the catalog's `data_path`; docs/auth.md now states that a broker must refuse a `prefix` outside the catalog's own placement, as hogtower's does. Under `ambient` or `static` with no template the Hoglite rehydrate only requeues: each call records a failed `hydrator` run whose error names the missing setting, so `GET /maintenance/status` shows it, and the server warns at boot when Hoglite backends are configured that way. A file outside the prefix is marked `failed` without being read. With the template set, creating a Hoglite catalog whose `data_path` is not the template with its name answers 422 `validation`, as PostgreSQL does for a bad `data_path`, and a catalog not at its placement (created before the template, or with a rewritten `data_path`) is not swept: its run is recorded failed naming both paths, and no file is marked `failed`. The broker session is resolved before the sweep claims a file, so a broker refusal fails the run once instead of costing one refused vend and one transient count per file; a session that cannot be vended mid-sweep stops the sweep with the file `pending` and not counted as `claimed`.

The sweep's footer reads are held to the tenant's registration, which the tenant can rewrite: the tail read is a closed range ending at `file_size_bytes`, a `footer_size` over new `HOGLAKE_HOGLITE_MAX_FOOTER_BYTES` (default 64 MiB) is not usable and the file takes the whole-object read under `HOGLAKE_HYDRATOR_MAX_WHOLE_OBJECT_BYTES` instead of pulling up to 2 GiB through the tail, and the whole-object read stops one byte past `file_size_bytes`, so an object longer than its registration is marked `failed` (re-register it with its real size, then rehydrate) instead of being read whole onto the heap. An object shorter than its registration is marked `failed` too (a tail start past its end answers 416, which was counted transient), so such a file rotates out of the sweep instead of staying `pending` and taking a slot on every call; a `file_size_bytes` under 8 bytes is `failed` before any read. PostgreSQL hydration reads as before; on both backends, the structural error for a file over the whole-object cap now names the tail read that did not parse when `footer_size` was usable, instead of saying it had none.
