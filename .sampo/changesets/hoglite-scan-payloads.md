hoglake: patch (Server)
---

A Hoglite scan serves an individual file whose stored statistics or split offsets exceed 64 KiB instead of refusing the plan with 422 (part of #685). Such payloads are read outside the 256-file page, in one query per batch of up to 16 MiB, not one per file. A payload read alone is no longer limited to Jackson's default 20M-character string, which failed a ~21 MiB one with 500, and a `stats_fields` page no longer holds every file's full narrowed statistics in hoglited only to drop the oversized ones. `stats_fields` now narrows the stored statistics inside the tenant, once per file, so every Hoglite scan budget counts only the requested fields: a one-field request over a table with hundreds of columns no longer pays for all of them. A Hoglite file listing no longer reads stored statistics or split offsets it does not return: it reads only the sort order's leading field, for ordering bounds, and a Hoglite partition lookup reads neither, so a listing page or a lookup's candidates of wide files or files with many split offsets no longer fail with 422 `backend_result_too_large`. A sorted listing page whose leading sort field alone is past hoglited's response cap (wide string bounds) is retried at half the size from the same cursor instead of failing with 422. A payload read alone that a concurrent type promotion widened after its page measured it is charged its fetched size, so the scan caps hold. The cumulative Hoglite scan caps are unchanged and still refuse with 422 scans PostgreSQL serves: 1M files, 512 MiB of response and 64 MiB of requested metadata, which a 1,000-column table with full statistics reaches at about 700 files, and files of 100,000 split offsets at about 64. #685 stays open for them; the README's backend table lists them.
