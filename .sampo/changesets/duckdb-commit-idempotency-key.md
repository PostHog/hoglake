The DuckDB extension sends an `idempotency_key` with every `/commit` when the catalog advertises `idempotent-append-v1`, minted once and fixed across the retries of one commit. A 503 `commit_outcome_unknown` (a Hoglite commit the server may have published) retried without a key registered the same parquet a second time and reported success; the retry now replays the receipt. A `/commit` whose answer is lost in transport (connection reset, read timeout, a proxy's 502/504) used to escape the retry loop as an `IOException`; it now retries under the same key within the same budget. A 500 on `/commit` is treated the same way: on the PostgreSQL backend a COMMIT whose acknowledgement the database connection lost is durable yet surfaces as a generic 500 (only Hoglite raises `commit_outcome_unknown`). Against a catalog without the capability no key is sent and these unknown outcomes are not retried, since a blind retry could double-register. Once any attempt's outcome is unknown the commit's terminal error, whatever the last attempt answered, says the commit may be durable, names the key and `GET /commit/receipts/{key}`, and states what that route guarantees (200 with the snapshot once published; a 404 is not proof either way, an attempt may still be in flight and receipts are purged after `HOGLAKE_RECEIPT_RETENTION_SECONDS`, so the table's contents or `hoglake_snapshots` decide before a re-run); that advice replaces a 409's "re-run the statement" suffix rather than following it. A commit attempt now waits `hoglake_commit_timeout_ms` (default 120 s, new setting) for its answer instead of 30 s, above the server's default commit-lock wait so a queued commit's clean 503 is heard rather than timed out, and the whole retry loop is bounded by `hoglake_commit_deadline_ms` (default 300 s, new setting) so retried timeouts cannot hold COMMIT for ~22 minutes against a hung server; it is capped at 30 minutes, half the server's minimum receipt retention, so a keyed retry never outlives its receipt. Only `commit_queue_timeout` and `backend_unavailable` 503s are retried as definite; any other 503 (a proxy's untyped one) is an unknown outcome. (#669)
