---
hoglake: patch (Server)
---

A Hoglite backend's 401 for a token hoglake accepted no longer answers 401 `invalid_token`, which made clients re-mint the token and retry into the same refusal. hoglake reads hoglite's clock from the refusal's `Date` header, which a pod that relays the owner's 401 stamps with its own clock, so each rule is judged on whichever of that and hoglake's clock reads it more strictly. A token whose `exp` has passed by hoglake's clock, or by more than hoglite's fixed 60 s by the `Date`, answers 401 `token_expired`. A token whose `iat` or `nbf` is more than those 60 s ahead of the earlier of the two clocks (hoglake accepts such a token only with `HOGLAKE_AUTH_CLOCK_SKEW_SECONDS` above 60 or a hoglite clock behind hoglake's) answers 503 `backend_unavailable` with no challenge and a `Retry-After` of the seconds until hoglite admits it (at most 300), so a client retries the same token, and a retry a hoglite pod with a trailing clock still refuses gets the rest of the wait; a token refused by an owner whose clock trails both hoglake's and the relaying pod's, and that leads neither by more than 60 s, is still answered as 403. Audit outcomes, and the counters that take them, record the 503 as `backend_token_not_yet_valid`, not as an outage. The first `/v1/query-batch` item that answers 401 is re-read on its own so that its refusal carries a `Date`, and that refusal fails the call without a re-read of each other refused item. A 401 after one of the request's transactions applied stays 503 `commit_outcome_unknown`. Any other answers 403 `backend_refused_authority` with no `WWW-Authenticate` challenge, because a new token with the same claims is refused again; a client may retry the same token after a delay, since a signing key hoglite has not fetched yet passes with time. The typed scoped reads map hoglite's 401 the same way instead of answering an outage's 503. The OpenAPI namespace, table and scan reads, the local-only namespace read included, list their 401 and 403 responses. docs/auth.md lists the rules hoglite applies on top of hoglake's, and the contract vectors carry hoglite's verdict as `backend_expect` on every accepted vector routed to it, with a verifier-only vector for each claim rule under which hoglake accepts a token and hoglite refuses it (#681).
