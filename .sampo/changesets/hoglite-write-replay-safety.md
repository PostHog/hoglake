---
hoglake: patch (Server)
---

A Hoglite write whose answer was lost after it may have applied answers 503 `commit_outcome_unknown` with a `Retry-After` header only when a blind replay of the request converges (#682). Each such write runs under a fresh backend txid, so a client that honoured the header replayed a new transaction. Replay-safe is the default; two classes of write now withhold the header, and their detail says to read before deciding: a commit WITHOUT an `idempotency_key` (duplicate paths are legal, so a replay registered the same files a second time; the detail says to send a key next time) and every DDL but a catalog drop (create a catalog; create or drop a namespace, table or view; truncate; alter), whose replay applied a second time (a truncate ended the files committed in between, a sort-order change re-applied) or met a refusal that read as its own failure (a create 409, a drop 404, an add-column 422). A commit under its `idempotency_key` keeps the header, as do the offset commit, options patch, containment, upload, table-creation and maintenance writes, and a catalog drop: its fence transaction opts out of the fence, so a replay passes the same emptiness guards and finishes the drop. PostgreSQL's lost COMMIT acknowledgement is a 500 that invites nothing; the two backends now agree on the invitation. This is part of #682, not all of it: no route gains an idempotency key, so a truncate whose outcome is unknown still cannot be retried exactly-once, and a client that retries every 503 regardless of the header still truncates twice. The optional key on the DDL and offset routes that the issue also asks for stays open under #682 itself. The DuckDB client's message for a 503 `commit_outcome_unknown` outside the commit loop no longer calls it retryable backpressure.
