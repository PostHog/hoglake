---
hoglake: patch (Server)
---

A Hoglite write whose answer was lost after it may have applied answers 503 `commit_outcome_unknown` with a `Retry-After` header only when a blind replay of the request converges (#682). Each such write runs under a fresh backend txid, so a client that honoured the header replayed a new transaction, after the original applied and after whatever another writer did in between. Replay-safe is the default; three classes of write now withhold the header, and their detail says to read before deciding: a commit WITHOUT an `idempotency_key` (duplicate paths are legal, so a replay registered the same files a second time; the detail says to send a key next time); an options patch, a containment mark or clear, and an offset commit, which set a value without a guard on the one they replace, so a replay undid a write that landed in between (a `consumer_floor` another operator re-enabled was disabled again, and expiry could pass active consumer offsets; a containment mark set in between was cleared) or was refused by it (409 `offset_regression` behind an offset another worker committed, for a write that applied); and every DDL (create or drop a catalog, namespace, table or view; truncate; alter), whose replay applied a second time (a truncate ended the files committed in between, a sort-order change re-applied, a catalog drop deleted a catalog another operator recreated under the same name after the drop finished) or met a refusal that read as its own failure (a create 409, a drop 404, an add-column 422). A catalog drop that fails after its fence applied, while releasing or deleting the tenant, now answers that same unknown outcome rather than a `backend_unavailable` with `Retry-After`, a 500 (an engine or proxy status the release does not expect), or a 422 that read as the drop's own refusal. An authority refusal there (a token that expired inside the drop, #680) keeps its 401 or 403, but its detail now says the catalog is fenced. A catalog read does not show the fence, so the drop's detail names what does: a fenced catalog answers every write 404 (it is being dropped), and DELETE again finishes that drop. A commit under its `idempotency_key` keeps the header, as do the upload and table-creation writes and the maintenance tasks; following it on a maintenance task runs the next batch (an expiry with `batch=1`, an `uploads/schedule-expired` with `limit=1`), which the OpenAPI document now says. The OpenAPI document also lists the 503 `commit_outcome_unknown` on the commit routes (no `Retry-After` on a keyless `/commit`), the containment mark, the options patch, and the expiry and compaction runs. An alter and a catalog create now read their result in their own transaction, as PostgreSQL's alter does. Before, they read it after the commit, so a read that spent its retry budget answered 503 `backend_unavailable` with `Retry-After`, which invited a replay of a DDL that had applied. PostgreSQL's lost COMMIT acknowledgement is a 500 that invites nothing; the two backends now agree on the invitation. This is part of #682, not all of it: no route gains an idempotency key, so a truncate whose outcome is unknown still cannot be retried exactly-once, and a client that retries every 503 regardless of the header still truncates twice. The optional key on the DDL and offset routes that the issue also asks for stays open under #682 itself. The DuckDB client's message for a 503 `commit_outcome_unknown` outside the commit loop no longer calls it retryable backpressure.
