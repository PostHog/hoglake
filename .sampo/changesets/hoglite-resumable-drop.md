Tests and docs for a Hoglite catalog drop that fails after its fence (#683). Retrying `DELETE /v1/catalogs/{catalog}` already completes such a drop (the fence transaction skips the `dropping` guard, so the retry re-proves the catalog empty, releases and deletes the tenant); a unit test and a live test now pin that. docs/auth.md, docs/auth-tenancy.md and the OpenAPI `dropCatalog` (which now lists the 403 and the Hoglite fenced state) state that dropping a Hoglite catalog needs a catalog-bound `operator` token, because hoglite deletes a tenant only for an operator; a `tenant` token with `admin` gets 403 before anything is fenced, and `dropCatalog` now carries a drop-specific 403 description saying so. The OpenAPI retry guidance covers only an original catalog still fenced: a retry from a replica with a lagging clock can answer 409 `catalog_not_empty` until it passes the expiry the first attempt saw, and a drop whose response was lost may already have deleted the tenant, so a retry can drop an empty catalog created since under the same name and routing. Tenant-admin self-service drop stays PostgreSQL-only (PostHog/hoglite#31).
